# HF-020: stale Manager files are not current health

Base `41dc00e`; independent branch `codex/hf020-manager-health-20261015`. This is distinct from HF-019's closed MCP-client readiness. A synthetic status marked connected/pending=0 but 55 minutes old was accepted as a handoff owner before repair; the regression failed. No private field receipt, identity or deployed path is published.

`inspectManagerStatus` reads the existing status file and ownership database without claiming or releasing anything. Online requires a valid recent timestamp, a live owner and an exact match of owner PID and Manager generation to the existing SQL meta authority, plus current running connection fields. Expired observations are stale, exited owners offline, and missing/corrupt/permission-unknown/future-time/generation-mismatched evidence unknown. Last-observed pending counts remain explicitly historical and do not represent compute threads or research completion.

The Manager records its generation in the existing generic meta table while it owns the store; no new DB/table/transport is introduced. Legacy readers ignore this key; health inspection of legacy records is conservative unknown. Generation mismatch prevents an older status file from identifying a replacement process as its owner. Handoff consumes the verified health and rechecks the same PID/generation before addressing the owner. Missing/stale evidence falls back to the existing normal SQL-owner wait, never a forced takeover.

The actual read-only consumer is `manager-cli <config.json> --status`, also exported through the existing router API and included by its existing builder. It requires no credentials or App context and starts no Manager, transport or research job. Installation guidance now uses this consumer instead of claiming health from raw status flags. Stopped status is never online. Permission uncertainty cannot be promoted to alive.

Acceptance covers a real owner subprocess exiting normally while the connected/pending=0 file remains fresh, a 55-minute stale observation, alive-but-expired, mismatched generation, malformed/missing evidence, stopped/degraded connections, unchanged status/database bytes on reads, no DB creation when absent, and the actual no-context CLI. A production Manager tick with fake connection adapters verifies generation publication and stopped shutdown. Source build succeeds through the existing router builder. The manager-health, manager-driver, lifecycle-handoff, session-lifecycle, harness-disconnect and harness-port suites report 28 passed, zero failed. npm run build produces the existing 43-file router package with 16 dependency license records.

Rollback preserves the existing queue/journal/status files; old code ignores the additional meta key but reintroduces stale-file admission. No existing owner is killed, service restarted, capsule closed, mailbox resolved or task resubmitted. Actual live state and native Linux are NOT RUN. Current provenance preserves historical source-map hashes; publication and diff checks pass. This is a source fix, not a live-health assertion about any historical host.
