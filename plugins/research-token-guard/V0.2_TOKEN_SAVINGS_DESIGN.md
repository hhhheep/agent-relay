# Research Token Guard v0.2: measurable token savings

Status: local implementation and provider pilot complete; remote deployment remains held pending a broader representative replay.

## Measured pilot status (2026-09-26)

- Clean synthetic cold A/B, GPT-6 Luna/high: identical answer hashes, identical cached input (14,080 tokens per arm), new input reduced from 29,518 to 16,316 (44.7253%), and total input reduced 30.2812%. This case passes the provider, correctness, and cache-comparability gates.
- Real multi-illumination record replay: identical answer hashes and total input reduced 14.1346%, but complete-task cached input differed by 50% between arms. The evaluator rejects its complete-task token claim as cache-confounded. The final response after tool output had equal cached input and 71.9786% lower new input, which is retained as a diagnostic mechanism result rather than promoted to a complete-task pass.
- The initial non-atomic guarded pilot increased new input by about 15.5% because the model needed repeated `--help`, path repair, and evidence commands. The atomic `stage_ledger.py execute` interface removed that orchestration overhead.

These results establish that savings have begun under a controlled equal-cache case. They do not yet establish the corpus-level 30% aggregate and 40% median gates required for remote rollout.

## Goal

Reduce the total model-facing input consumed by a complete research stage without changing the command, hiding evidence, weakening acceptance checks, or changing the supported scientific decision.

The goal is complete only after a controlled A/B replay records actual provider-reported token usage and passes every correctness gate below. Fewer returned bytes alone are useful instrumentation, but are not proof of actual token savings.

## Non-goals

- Do not replace scientific review with a summarizer.
- Do not send evidence to a second model for compression.
- Do not install a large orchestration framework merely to copy its architecture.
- Do not globally intercept every command before replay validation.
- Do not treat cached input tokens as equal to new input tokens or convert bytes to billing claims.

## What v0.1 proves and does not prove

v0.1 captures stdout and stderr exactly, stores hashes, returns a bounded receipt, retrieves exact excerpts, and detects tampering. Its tests prove recoverability and bounded command output.

v0.1 does not measure or control:

- repeated file reads and searches;
- repeated inclusion of unchanged evidence in later turns;
- message, turn, retry, time, or cost budgets;
- content-addressed reuse of a previously verified result;
- task identity across code, inputs, configuration, and working-tree state;
- total provider-reported input tokens for a complete task;
- correctness parity between an ordinary Codex task and a guarded task.

## Design sources

Borrow the design patterns, not their full dependency stacks:

- Aider: token-budgeted structural maps and relevance-ranked context.
- SWE-agent: an agent-computer interface with bounded file views, terse search output, and replayable trajectories.
- OpenHands: an append-only event history with model-facing derived views.
- Inspect AI: enforced message, token, turn, time, working-time, and cost limits plus scored submissions.
- LangGraph: durable checkpoints and explicit interrupt/resume boundaries.
- Prefect: content-derived cache keys, persisted results, retry state, and idempotent reuse.

## Minimum viable v0.2

Implement a narrow vertical slice before adding repo maps or semantic retrieval.

### 1. Append-only event ledger

Use Python's standard-library SQLite with WAL mode. Store an immutable event for each stage start, guarded command, exact retrieval, verification, decision, and stage close. Raw streams remain ordinary files; the ledger stores their relative paths, sizes, hashes, and provenance.

Each event contains:

- schema version and event type;
- stage and task identifiers;
- monotonic sequence number and timestamp;
- canonical payload hash;
- parent event hash;
- model-facing byte count;
- raw evidence references rather than duplicated raw content.

The hash chain detects missing or reordered events. It does not replace the existing raw-stream hashes.

### 2. Content-derived task fingerprint

Before reuse, calculate a canonical fingerprint from:

- stage objective and acceptance checks;
- normalized command argument vector;
- relative working directory;
- declared input file hashes;
- relevant source/configuration hashes;
- Git HEAD when available and a dirty-patch hash when applicable;
- tool schema and implementation version;
- an allowlisted runtime description.

Never include secrets or hash the entire environment. A cache hit is permitted only when the complete fingerprint matches and every referenced artifact still verifies.

### 3. Deterministic context views

Generate model-facing views from the ledger rather than rewriting prose repeatedly:

- `status`: current state, budget balance, failures, and unresolved checks;
- `evidence`: exact requested lines with source hashes and coordinates;
- `change`: only events and artifacts added since a known event hash;
- `handoff`: decision, verified evidence, uncertainty, and next bounded action;
- `audit`: full event index without embedding raw streams.

Every view records its source event range, view policy version, raw byte total, returned byte total, and SHA-256. A view may omit content but cannot assert a scientific interpretation.

### 4. Enforced stage state and budgets

Use an explicit state machine:

```text
planned -> running -> needs_review -> accepted
                              |-----> rejected
                              |-----> deferred
running -> failed
```

The stage specification must set limits for:

- model turns;
- tool/command calls;
- retries per identical fingerprint;
- returned model-facing bytes;
- wall time;
- optional provider input/output tokens and cost when observable.

Crossing a hard limit stops with `needs_review`; it does not silently relax the limit. Failure repair requires exact verified evidence. The orchestrator, not the model, waits for long-running processes.

### 5. Evidence-first cache

On a valid cache hit:

- do not rerun the command;
- emit a cache-hit event referencing the original verified receipt;
- return the current bounded view;
- preserve the original execution time and identity.

Any changed declared input, source/configuration hash, command, acceptance check, schema version, or missing/tampered artifact invalidates the entry. Failed and timed-out runs are not reusable as successful results.

## Replay corpus

Build fixtures from saved, non-secret artifacts. Do not start new GPU jobs for the benchmark. The corpus must contain at least these eight cases:

1. large successful log with a metric near the end;
2. traceback embedded in noisy output;
3. ablation table with multiple candidate and baseline values;
4. small output that must remain byte-exact;
5. invalid UTF-8 or binary-like output;
6. repeated request for an unchanged file or result;
7. one-byte input mutation that must invalidate the cache;
8. a go/stop/defer decision grounded in several evidence files.

Each case defines an answer key containing required facts, required evidence coordinates, expected failure classification, and expected gate decision. Answer keys are deterministic data, not model-written summaries.

## Controlled A/B

Run two fresh tasks with the same Codex model, reasoning setting, starting state, prompt, permissions, and fixture corpus.

### A: baseline

Use the current ordinary workplace flow. Preserve provider usage events and the exact files/tool outputs placed in model context.

### B: v0.2

Use the event ledger, fingerprint cache, bounded views, and enforced budgets. Do not change the scientific prompt or answer key.

Record per task:

- provider-reported new input tokens;
- provider-reported cached input tokens;
- output/reasoning tokens when exposed;
- model turns and tool calls;
- raw and model-facing bytes;
- cache hits, invalidations, and command executions;
- wall time;
- answer-key fact recall;
- evidence-coordinate match;
- failure classification;
- final gate decision.

If per-request usage is unavailable, the run may establish byte/tokenizer-proxy savings but cannot satisfy the final goal. Provider-reported usage is required before claiming actual token savings.

## Acceptance gates

Correctness gates are absolute and evaluated first:

- 100% of raw stdout/stderr hashes verify.
- 100% of required answer-key facts are present and correct.
- 100% of required evidence coordinates resolve to exact source content.
- All failure classifications match the baseline.
- All go/stop/defer decisions match the answer key.
- Small valid UTF-8 output remains byte-exact.
- Cache invalidation has zero false hits in the mutation cases.
- No experiment or command is rerun solely because a view omitted content.

Only after those pass, require efficiency:

- at least 30% lower aggregate provider-reported new input tokens;
- at least 40% lower median new input tokens per replay case;
- no increase in aggregate command executions;
- no more than one additional retrieval turn in any case;
- bounded-view generation adds no paid-model call.

Report cached input separately. Cost can be reported only from the provider's documented accounting; do not infer it from the token count.

## Implementation order

1. Add the replay corpus, deterministic answer keys, and a baseline recorder.
2. Add the SQLite event ledger and generate the current stage receipt from it.
3. Add task fingerprints, artifact verification, and cache invalidation tests.
4. Add deterministic `status`, `evidence`, `change`, and `handoff` views.
5. Add hard stage budgets and state transitions.
6. Run offline replay until all correctness gates pass and model-facing bytes decrease.
7. Run the same-model provider-measured A/B on fresh tasks.
8. Deploy to remote 91 only after the final token gates pass, or label it explicitly as an instrumentation pilot.

## Stop conditions

Stop and redesign rather than deploy when any of these occurs:

- a required fact or error disappears from the bounded view and cannot be deterministically retrieved;
- a cache hit survives an input or code mutation;
- a gate decision differs from the answer key;
- token usage falls only because the guarded run performs less required work;
- savings exist only in byte estimates but not in provider usage;
- orchestration complexity causes more turns or reruns than it removes.
